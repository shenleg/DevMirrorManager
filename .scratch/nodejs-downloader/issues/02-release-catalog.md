# 官方版本目录与当前受支持 LTS 的判定依据

Type: research
Labels: wayfinder:research
Status: resolved
Blocked by: none
Assignee: collin

本议题调查发行版本、可用分发文件与支持周期的数据契约，不设计最终页面交互。

## Question

如何从官方来源可靠得到可搜索的发行版本、每个版本真实存在的操作系统/架构/文件格式组合，以及查询时仍受支持的 LTS 范围？

调查 `https://nodejs.org/dist/` 及 Node.js 官方维护的生命周期数据，明确：

- 官方索引字段、排序、LTS 标记语义、`files` 标识与实际分发文件名的关系；索引是否足以确定全部格式，何时需补查目录。
- 当前受支持的 LTS 必须结合发布线的时间表和发行版本自己的 LTS 标记；进入 LTS 前的发行版本、Current、Maintenance、EOL、未来时间表分别如何判定。
- 数据来源的稳定性、更新方式、缓存与查询失败时有哪些事实限制；不能只靠 `lts != false` 或静态主版本列表。
- macOS/Windows/Linux 的目标架构和常用格式有哪些缺失、变迁或特殊情况；禁止凭操作系统×架构×格式的笛卡尔积生成并不存在的 URL。
- 搜索文本、完整版本号和主版本号所需信息是否都可从官方数据取得。
- 用少量真实索引记录和文件列表验证结论，不下载分发包。

证据保存在 [官方版本与生命周期调研](../research/release-catalog.md)。注明观察日期，并将算法可依赖的契约与当天的版本快照分开。

## Answer

事实调研已完成，详见 [官方版本与生命周期调研](../research/release-catalog.md)。已用官方 JSON/TSV、发布线时间表、版本校验清单、目录及索引生成器源码交叉核对，核心结论如下：

- `lts` 来自发行版本的源码标记，不是当前支持状态。当前受支持 LTS 须结合该标记与发布线 `schedule.json` 的支持周期；不能仅用 `lts != false`、偶数主版本或静态版本列表。
- 按 2026-10-13 会话日期和取得的时间表，v22 为 Maintenance LTS、v24 为 Active LTS，v20 已 EOL，v26 尚为 Current；这仅是调研快照。v24.10.0 即使属于仍受支持的 v24 发布线，也因自身 `lts: false` 应排除。
- 索引 `files` 是转换后的类别，不是完整文件集合。`.tar.gz` 与 `.tar.xz` 不能仅靠一个类别逐项枚举，且 `win-arm64/node.exe` 实际存在但当前映射未产生对应 exe token。应依据版本原始 `SHASUMS256.txt` 枚举真实路径，目录用于大小和交叉验证。
- v22 与 v24 的 Windows x86/Linux armv7l 可用性不同；同一发行版本还可能同时有 `linux-x64` 与 `linux-x64-musl`。不能生成目标组合笛卡尔积，也不能将 libc 变体静默合并。
- 官方已宣布自 v27 改为年度周期，每个主版本最终进入 LTS；旧 README 的奇偶描述未完全同步。当前 v27 时间表尚无 `lts` 字段，须按未知处理，不推断永久非 LTS。
- 官方时间表可能改变。索引和生命周期需分别更新，且支持状态需随查询时钟重新计算。本次响应 `Date` 为 2026-10-12，会话日期为 2026-10-13；报告记录差异，未假装来源在当天实时更新。

残留产品决定：日期转换的时区和结束日边界、缺失/过期生命周期数据的降级、Linux libc 变体范围、支持线内旧补丁与最新安全补丁提示、清单获取时机与失败行为。官方时间表只给日期，UTC 和 `[lts, end)` 是可选产品规则而非已验证官方精确时刻。支持发布线也不代表每个旧补丁含有最新安全修复。
