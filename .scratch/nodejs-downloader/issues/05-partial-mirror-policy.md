# 部分镜像的索引、校验文件与可用性承诺

Type: grilling
Labels: wayfinder:grilling
Status: resolved
Blocked by: 01, 02
Assignee: collin

本议题决定选择性导出与 nvm 消费者之间的内容契约，落实用户已确认的“镜像版本发现反映实际下载内容”，而不是只要求目录长得像官方源。

## Question

在镜像索引必须以实际已完成并通过校验的内容为依据、不得宣称未下载内容可用的前提下，怎样满足约定 nvm 客户端的版本发现、精确安装、别名解析和文件完整性需求？

已确认的需求输入：用户补充需求中的“根据下载的内容列出内容”指 nvm 配置镜像后看到的可用版本与内容（A），不由本项推出应用镜像地址设置页或代为配置 nvm 的要求。未完成、校验失败或不存在的文件不能被列为可用；某版本只有部分目标平台文件时，不能宣称其余目标组合也可用。该输入不是本议题全部取舍的解决结果。

根据 [nvm 双客户端与 Nexus 路径的兼容契约](01-mirror-protocol.md) 和 [官方版本目录与当前受支持 LTS 的判定依据](02-release-catalog.md)，与用户决定：

- 首先明确客户端兼容版本与安装环境范围：当前 nvm-windows `v2.0.1` 的 `.7z`/`index.tab` 契约、旧版 `1.2.2` 的 ZIP/`index.json` 与 `latest/SHASUMS256.txt` 差异，以及 nvm-sh 的 `.tar.xz`/`.tar.gz` 环境差异。是否覆盖旧版、是否自动补齐所承诺客户端必需格式，均待用户选择。
- 如何从镜像可用内容生成客户端可读的子集索引，保留哪些官方字段；上游全量目录可用于下载候选或内部缓存，但不能未经筛选作为镜像可用索引发布。
- 某版本仅备有部分系统、架构或格式时，索引如何表达、兼容承诺如何限定，`latest`、LTS 别名及旧版 discovery 文件如何处理。客户端可能不按平台文件列过滤，不能仅裁剪一列便宣称跨平台别名安装成立。
- 官方校验文件和签名如何保存；保留原始校验清单中未下载的条目不等于在镜像索引中宣称它们可用，修改清单后不能仍声称具有原始签名真实性。
- 下载失败、取消、校验成功后的文件提交、镜像追加和索引更新之间怎样保持内容与可用声明一致；未来上传所需的发布条件只作为导出契约，不实现 Nexus 上传。
- UI 的 LTS 过滤与已导出历史内容及其索引如何区分；不得默认删除文件，也不能把“在受支持发布线中”当作“已经下载”。
- Nexus 需要具备哪些路径、浏览和下载访问条件，才能满足已选择的 nvm 消费方式；API 仓库选择、认证配置与上传实现不属于第一阶段。

这里只作决策，不实现索引生成、不上传 Nexus。加载 `grilling` 和 `domain-modeling`，由用户确认剩余取舍。

## Answer

用户于 2026-10-13 确认以下最终契约。事实依据见 [nvm 与 Nexus 兼容调研](../research/mirror-protocol.md) 和 [官方版本与生命周期调研](../research/release-catalog.md)。本答案决定镜像导出与消费边界，不表示实际客户端或 Nexus 端到端验收已经通过。

### 1. 客户端与必需文件

- 第一版承诺 nvm-sh `v0.40.8` 与 nvm-windows `v2.0.1` 的标准在线二进制安装请求契约；不承诺旧版客户端、源码构建或完全离线安装。
- 所选 macOS/Linux 目标平台必须具备对应官方 `.tar.xz` 与 `.tar.gz`，覆盖 nvm-sh 随客户端环境选择压缩格式的差异；所选 Windows 目标平台必须具备对应官方 `.7z`，满足 nvm-windows `v2.0.1` 标准在线安装路径。
- 选择目标平台时，界面明确展示并勾选必需格式，必需格式不可取消；其他真实存在的格式仍可选。不自动下载未选目标平台，也不将 ZIP、安装器或源码作为必需格式的替代品。
- 上游缺少该目标平台任一必需文件时，该平台不能被声明为可安装；界面说明原因，不生成不存在的 URL。具体支持哪些架构和分发变体，继续由 [同一目标平台的分发变体支持范围](10-distribution-variants.md) 决定；本答案不扩大其支持范围。

### 2. 单一入口与合并索引

- 镜像根目录保持为用户所选输出根目录下的 `nodejs/`，保留官方分发文件名和版本目录内的相对路径，不解压、不改名。所有客户端共用一个镜像根 URL，不生成分平台镜像入口。
- 每个发行版本只要至少一个所选目标平台的必需文件全部成为校验通过的正式文件，并具备对应官方校验清单，即可进入共享 `index.tab`。不要求其他目标平台齐备，也不要求整批发行版本全部成功。
- 只有额外可选文件、缺少该平台必需格式时，不足以支撑该平台可安装或使一个尚无可安装平台的发行版本进入索引。
- 可以继续追加发行版本、目标平台与可选格式；每次按实际内容重新生成索引。不固定镜像的平台覆盖范围，不设置跨平台补齐门槛。
- `index.tab` 保留客户端所需的官方表头和字段结构，按发行版本号降序排列，保留官方日期、npm、LTS 名称及其他事实字段。`files` 按官方类别映射如实表达已完成、校验通过的实际文件，不照搬上游全量字段，不虚构不存在的类别；该列不能完整表达格式齐备或代替平台可安装性判断。
- 上游全量目录只用于下载候选或内部缓存，不作为镜像可用索引发布。第一版不生成旧版专用的 `index.json` 或 `latest/` discovery 文件。

### 3. 发现、精确安装与别名的限制

- 合并索引表达“至少一个目标平台可安装的发行版本并集”，而不是“每个访问客户端都能安装的发行版本集合”。索引中出现一个发行版本，不代表它的所有目标平台均可用。
- 用户明确接受 nvm 可能列出只有其他平台文件的发行版本；裁剪 `files` 不会使所承诺客户端可靠地按本机平台过滤发现结果。
- 精确版本二进制安装要求镜像具备客户端实际请求的本机目标平台文件及对应校验清单；不承诺在文件缺失时自动下载其他平台文件、回源或完成源码构建。
- `latest`、LTS、主版本等选择由客户端根据共享镜像子集解析，不追随尚未下载的上游发行版本。“镜像最新”不等于“官方最新”。不承诺别名选择一定适用于本机，也不承诺客户端自动寻找本机可安装的次新版本。
- 客户端可能缓存旧索引，不承诺本地或远端更新立即对所有客户端生效。实际兼容结果仍需在后续验收中验证。

### 4. 校验清单与签名

- 从官方 HTTPS 来源获取每个发行版本的 `SHASUMS256.txt`，原样保留字节，允许其中包含未下载文件的校验条目。校验清单是预期 hash 的依据，不是镜像可用内容列表。
- 每个分发文件必须匹配官方清单中的路径和 SHA-256，校验成功才可成为镜像可用内容；不将请求完成、文件大小正常或客户端自身可能跳过校验视为应用的校验保障。
- 原样保存官方提供的 `.asc`、`.sig` 签名附件；附件获取失败时明确告警，但不阻止已满足其他条件的内容进入索引，不生成或冒充官方签名。
- 第一版不执行 PGP 签名验证，不声称“官方签名验证通过”。通过 HTTPS 取得清单并进行 SHA-256 对比不等于独立验证发布者真实性；可信密钥、更新与撤销机制及 PGP 验证能力留待后续。

### 5. 已有目录、追加与重新核验

- 新建镜像要求 `nodejs/` 不存在或为空；已有应用管理记录的镜像可以继续追加，不自动接管用户手工拼装的目录。
- 管理记录与临时下载内容放在 `nodejs/` 外，不混入未来上传的镜像文件。具体记录结构与路径由后续技术路线决定。
- 每次更新索引前，重新检查将被声明可用的全部必需文件及其 SHA-256，不只依赖上一次成功记录。这会增加本地读取时间，作为第一版一致性保障的明确代价。
- 必需文件被外部删除或修改后，对应平台不再支撑可用声明；若该发行版本仍有其他平台齐备，则继续保留索引行，否则不再收录。对索引中的可选文件类别也不得沿用未经核验的旧可用声明。
- 未登记文件不自动纳入索引，也不自动删除；同路径内容冲突时停止该项并提示用户，不静默覆盖。损坏内容不再支撑可用声明，不默认删除或替换原文件。
- 本答案只确定数据保护与可用性原则；取消、重试、恢复、重启以及索引更新失败后的协调机制由 [下载任务的恢复、失败与完成语义](06-download-lifecycle.md) 继续决定，不在本议题预设事务或持久化实现。

### 6. 批量结果与 LTS 筛选

- 批量允许部分成功：满足收录条件的发行版本可发布，失败、取消、未完成或校验失败的内容不得支撑可用声明。一个发行版本内某个平台失败，不妨碍其他已经齐备的平台使该发行版本收录。
- 已有可用内容不因不相关的新下载失败而撤回；若重新核验发现已有内容失效，则按实际剩余可用平台更新索引。
- 应用中的“仅显示当前受支持 LTS”只过滤下载候选，不自动删除已导出文件、不因发布线 EOL 自动撤下仍满足可用条件的索引行，也不修改官方 LTS 标记。
- nvm 自身的 LTS 别名不判定官方支持周期，不能将它宣传为应用的“当前受支持 LTS”筛选。生命周期数据失效、日期边界等由 [生命周期数据失效与 LTS 筛选的边界策略](09-lts-data-policy.md) 继续决定。

### 7. 本地交付与未来上传前提

- 本地先准备校验通过的正式分发文件及对应校验清单，再完整替换 `index.tab`；不能发布半写入的索引。具体替换、恢复和并发规则由后续议题选择。
- 应用明确区分“正在准备”和“可交付”，列明可用发行版本、可用目标平台及未完成项。整批部分失败不妨碍已满足条件的子集形成可交付镜像，但尚有本地写入时不作为完成的镜像交给上传流程。
- 交付给未来上传流程时，停止对该镜像根的写入；本阶段不实现上传、快照或远端事务。
- 未来上传必须先确认分发内容与校验文件上传成功，最后发布索引；Nexus 路径结构不等于整批原子发布，上传结束不等于客户端兼容验收通过。
- 上传路径以 `nodejs/` 内相对路径为准，镜像 URL 必须指向实际内容根。第一版消费前提为客户端可通过匿名 HTTPS 只读访问明确的索引、校验文件和分发文件 URL，无需交互登录或额外下载认证配置；不要求上传接口匿名。
- 不依赖 Nexus 模拟官方目录 HTML、软链接或 `latest/` 目录。需要认证的下载方案、实例权限配置和真实客户端验收在后续阶段处理，本阶段不调用 Nexus API。
