# 第一版验收边界与开发规格的充分性

Type: grilling
Labels: wayfinder:grilling
Status: open
Blocked by: 04, 05, 06, 07, 11
Assignee: none

本议题确认第一阶段路线何时足以交给开发，验证用户必须需求而不把后续运行时、Nexus API 上传和生产发布混入第一版验收。

## Question

在选择交互、部分镜像内容契约、下载生命周期与实现边界明确后，第一版的验收必须覆盖哪些场景，才能证明 Node.js 下载、当前受支持 LTS/目标平台筛选、目录选择和内容驱动镜像索引均兑现了用户要求？哪些决定仍不足以写成可执行开发规格？

结合 [搜索、多选与目标平台组合的交互模型](04-selection-interaction.md)、[部分镜像的索引、校验文件与可用性承诺](05-partial-mirror-policy.md)、[下载任务的恢复、失败与完成语义](06-download-lifecycle.md) 和 [前端技术栈与下载引擎的职责边界](07-implementation-boundaries.md)，与用户确认：

- 版本搜索、批量选择、当前受支持 LTS 的时间边界及未知支持状态；EOL 与发行版本自身不带 LTS 标记的情况不能因所属主版本或历史标签而误入筛选。
- 指定系统/架构与文件格式，不存在的目标组合、部分失败、校验失败和重复下载。
- 用户选择的非仓库输出目录，`nodejs/` 下的原始相对路径，以及目录改变、不可写和已有内容保护。
- 镜像索引与实际已完成且校验通过的内容一致；未下载、未完成、校验失败的内容不能被宣称可用。只下载部分平台时，如何证明发现与安装行为符合限定的兼容承诺。
- 首次下载、追加下载、取消、索引生成失败和重启之后，哪些内容与索引一致性场景必须覆盖；不仅检查下载列表显示成功。
- 两个 nvm 客户端各自必须成功的使用场景、固定验收客户端版本/环境、压缩格式和别名发现行为，以及 Nexus 路径映射的必要前提。旧版 Windows 的外部 npm 获取和新版其他外围联网不能被默认为已实现完全离线；源码请求契约不等于真实客户端验收已通过。
- 如何验证镜像消费契约而不依赖尚未实现的 Nexus API 上传；第一版不以 Python/uv、Go/voidint/g 或 API 仓库选择为验收条件。
- macOS 与 Windows 上分别需要怎样的自动化与真实桌面验证。
- 是否仍有阻止第一阶段开发的决定；若有，仅将已可精确描述的问题建立新议题，其余保留为本阶段地图中的雾区，不把后续阶段需求加回雾区。

加载 `grilling` 与 `domain-modeling`。本议题的答案记录验收与交接决策，不实际执行下载、安装、上传或发布。
